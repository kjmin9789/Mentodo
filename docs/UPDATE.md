# 정기 갱신과 이어서 수집

Mentodo를 설치한 뒤 각자의 Codex에서 수집 자동화를 등록합니다. 앱의 Python 서버에는 Discord 수집기나 예약 실행기가 포함되어 있지 않습니다. 다른 사람의 예약, 로그인, 수집 기록은 설치본에 복사되지 않습니다.

## 언제 갱신하나요?

| 작업 | 주기 | 실행하는 곳 |
| --- | --- | --- |
| 새 대화 수집·미완료 후속 확인 | 매일 09:00·12:00·17:00, Asia/Seoul 기준으로 등록 | 각자의 Codex 자동화 |
| 저장된 업무를 화면에 반영 | 화면으로 돌아올 때, 화면이 보이는 동안 1분마다 | Mentodo 화면 |
| 다른 브라우저의 완료·되돌리기 반영 | 화면으로 돌아올 때, 화면이 보이는 동안 5초마다 | Mentodo 화면 |

수집 일정은 자신의 업무 시간에 맞게 바꿀 수 있습니다. 자동화가 실행될 때 컴퓨터와 Codex가 실행 가능한 상태여야 하고, 대상 서비스에 로그인되어 있어야 합니다. 로그인이 풀리면 기존 탭에서 다시 로그인하고 수집을 재실행합니다. 서버가 꺼져 있어도 수집 파일은 갱신할 수 있지만, 화면을 보려면 서버를 실행해야 합니다.

## 1. 본인 범위로 예약 등록

아래 내용을 Mentodo 폴더를 연 Codex 채팅에 붙여넣습니다. 대괄호를 실제 값으로 바꾸고, 완료 안내에서 일정·시간대와 활성 상태를 확인합니다. 자동화 기능이나 브라우저 도구가 없는 환경에서는 이 프롬프트만으로 예약 수집을 실행할 수 없으므로 수동 수집을 사용합니다.

```text
이 프로젝트의 README.md, docs/COLLECT.md, docs/DATA.md, docs/UPDATE.md를 읽고
내 Mentodo 데이터를 갱신하는 정기 자동화를 이 채팅에 등록해 줘.

프로젝트 절대 경로: [본인 컴퓨터의 Mentodo 폴더 경로]
내 계정: [Discord 사용자명 / 서버 별명]
수집 범위: [서버·채널, DM은 포함할 때만 명시]
첫 수집 시작일: [YYYY-MM-DD]
내 프로젝트 목록: [본인 업무에 맞게 지정 / 처음이면 대화 맥락으로 분리]
예외 통합: [명시적으로 합칠 프로젝트만 / 기본은 없음]
기존 로그인 브라우저·스페이스: [사용할 브라우저와 기존 탭 또는 스페이스]
일정: 매일 09:00, 12:00, 17:00 / 시간대 Asia/Seoul

매 실행에서 docs/UPDATE.md의 이어서 수집하는 절차를 따라 줘.
받은 직접·역할 멘션과 내가 작성한 요청·질문·공유를 모두 확인하고,
앞뒤 맥락으로 분류해 줘. 마지막 성공 지점 이후 새 대화를 추가하고
기존 미완료 항목은 원래 날짜와 관계없이 후속 대화와 PR을 확인해 줘.
같은 작업은 ID를 유지하고 리마인드나 후속 알림은 기존 항목에 합쳐 줘.
내가 직접 완료하거나 되돌린 local/state.json은 바꾸지 마.
모든 확인과 데이터 저장이 성공했을 때만 수집 지점을 전진시켜 줘.

기존 로그인 세션을 재사용하고 새 세션을 만들거나 쿠키를 초기화하지 마.
로그인이 필요하면 기존 탭에서 내가 로그인할 수 있게 알려줘.
메시지나 댓글은 게시하지 말고 개인 데이터는 Git에 올리지 마.
추가·완료·실패 또는 내 조치가 필요한 경우에만 알리고,
변동이 없으면 조용히 끝내 줘.
```

## 제목 옆 업데이트 버튼으로 수동 수집

**업데이트** 버튼은 저장된 목록만 다시 읽는 대신, 로컬에 설정한 수집 명령을 실행합니다. 실행 중에는 **업데이트 중…**으로 표시하고 같은 버튼의 중복 실행을 막습니다. 수집 완료 기록이 새로 저장되면 목록을 다시 읽습니다. 실패하면 오류를 알리고 기존 업무·수동 상태를 유지합니다. 공유받은 다른 컴퓨터에서는 실행할 수 없습니다.

한 번 설정하려면 Codex에게 아래와 같이 요청합니다.

```text
내 Mentodo 폴더에 수동 업데이트 버튼의 수집 명령을 설정해 줘.
local/collector.json의 command에 셸 문자열 대신 실행 파일과 인수를 배열로 저장해 줘.
이미 로그인한 Codex CLI의 실제 실행 경로를 확인하고 codex exec를 사용해 줘.
프로젝트 폴더와 local/에만 필요한 쓰기 권한을 주고, 브라우저 연결에 필요한 네트워크를 허용해 줘.
작업 프롬프트에 내 계정·수집 범위·기존 로그인 브라우저와 docs/UPDATE.md 절차를 포함해 줘.
새 대화 수집 및 미완료 후속 확인만 수행하고 코드 변경이나 메시지·댓글 게시를 금지해 줘.
이 실행의 collection.lock은 부모 서버가 소유하므로 직접 만들거나 삭제하지 않도록 알려줘.
모든 확인·검증·저장이 성공할 때만 local/collection.json의 lastSuccessfulRunAt을 갱신하게 해 줘.
개인 설정은 Git에 올리지 마.
```

설정 형식은 다음과 같습니다. 경로와 수집 프롬프트는 본인 환경으로 바꿉니다. Codex CLI 설치 및 로그인 상태를 먼저 확인합니다. 명령 실행에는 본인의 Codex 사용량이 사용됩니다. [공식 비대화형 실행 안내](https://learn.chatgpt.com/docs/non-interactive-mode)를 참고할 수 있습니다.

```json
{
  "command": [
    "/본인/환경의/codex",
    "exec",
    "--ephemeral",
    "--sandbox", "workspace-write",
    "-c", "sandbox_workspace_write.network_access=true",
    "--cd", "/본인/Mentodo",
    "docs/UPDATE.md와 docs/COLLECT.md를 읽고 본인의 설정된 범위를 수집한다. collection.lock은 부모 서버가 소유하므로 직접 획득·삭제하지 않는다. 모든 조회·검증·저장이 성공할 때만 local/collection.json의 lastSuccessfulRunAt과 resumeAfter를 갱신한다."
  ]
}
```

서버는 `local/collector.json`만 읽으며 브라우저에서 실행 명령을 전달받지 않습니다. 설정이 없으면 버튼에 설정 안내가 표시됩니다. 실행 로그는 Git에서 제외되는 `local/collector.log`에 저장됩니다. 로그인 문제나 실패 원인은 이 로그에서 확인합니다. 실행 제한은 30분이며 시간 초과 시 성공으로 표시하지 않습니다.

## 2. 이어서 수집하는 절차

이 절차는 예약을 실행하는 수집 도구가 따릅니다. Mentodo 서버는 `collection.json`을 생성하거나 수집 경계를 자동 변경하지 않습니다.

1. 정기 수집은 `local/collection.lock`을 원자적으로 생성해 잠금을 획득합니다. 이미 있으면 수집 중이므로 이번 실행을 건너뜁니다. 수동 버튼 실행은 부모 서버가 잠금을 관리하므로 수집 명령에서 다시 획득하거나 제거하지 않습니다. 정기 수집은 종료할 때 자신의 잠금을 제거합니다. 실행 시작 시각과 수집 범위를 확인하고 `local/tasks.json`, `local/state.json`, `local/collection.json`을 읽습니다.
2. 기록이 있다면 `resumeAfter` 이후부터 이번 실행 시작 시각까지 새 메시지를 확인합니다. 날짜 단위 검색 결과는 실제 메시지 시각이나 Discord 메시지 ID로 경계를 다시 비교합니다. 기록이 없고 기존 업무만 있다면 마지막 업무의 원문 작성 시각부터 이어서 확인합니다. 둘 다 없으면 사용자가 지정한 첫 시작일부터 수집합니다.
3. 원문 메시지 ID와 기존 업무·근거 링크로 중복을 제거합니다. 다른 날짜의 기존 업무도 보존하며 같은 작업의 ID를 바꾸지 않습니다. 미완료 업무는 원래 요청이 오래됐더라도 연결된 스레드와 PR의 후속 결과를 확인합니다.
4. 단순 답변·반응만으로 완료하지 않습니다. 실제 해결 근거를 `note`와 `evidence`에 남깁니다. `local/state.json`의 직접 완료·되돌리기 상태는 유지하고, 충돌하는 새 근거가 있으면 사용자에게 알립니다.
5. `local/tasks.json` 전체를 임시 파일에 작성하고 JSON 형식과 `server.py`의 `validate_tasks`로 검증한 뒤 원자적으로 교체합니다. 이어서 `python3 server.py --check`를 실행합니다. Windows에서는 `py -3`을 사용합니다.
6. 모든 범위의 확인과 업무 파일 저장이 성공한 뒤에만 `resumeAfter`를 이번 실행 시작 시각으로 옮깁니다. 메시지가 0건이어도 해당 구간을 끝까지 확인했다면 전진할 수 있습니다. `knownSourceMessageIds`를 합치고 실제 완료 시각을 `lastSuccessfulRunAt`에 기록합니다. 이 파일도 임시 파일과 원자적 교체로 저장합니다.

일부 채널 접근이나 검색이 실패하면 성공한 항목을 보존하되 수집 경계를 전진시키지 않습니다. 다음 실행에서 같은 구간을 다시 확인하고 중복을 제거합니다. 이렇게 해야 확인하지 못한 대화를 건너뛰지 않습니다.

수집 범위에 서버·채널을 추가하면 기존 경계가 새 범위까지 확인했다는 뜻은 아닙니다. 새 범위의 시작일을 별도로 정해 과거 내용을 확인한 뒤 경계를 갱신합니다. 여러 자동화가 같은 폴더를 동시에 수정하지 않도록 한 사용자당 하나의 수집 예약을 사용합니다. 비정상 종료 뒤 잠금이 남으면 실제 수집 프로세스가 종료됐는지 확인한 뒤 제거합니다.

## 수집 기록 형식

아래는 형식 예시입니다. 최초 등록할 때 미래 시각이나 지금 시각을 임의로 입력하면 그 이전 대화를 놓칠 수 있으므로, 실제 첫 수집을 마친 도구가 기록하게 합니다. 기존 파일을 초기화할 필요는 없습니다.

```json
{
  "timezone": "Asia/Seoul",
  "scope": {
    "account": "내 Discord 계정",
    "sources": ["내가 지정한 서버·채널"]
  },
  "resumeAfter": "2026-10-22T00:00:00+09:00",
  "knownSourceMessageIds": [],
  "lastSuccessfulRunAt": "2026-10-22T09:05:00+09:00"
}
```

`resumeAfter`는 확인을 끝낸 구간의 끝이고, `lastSuccessfulRunAt`은 작업을 마친 시각입니다. 두 값을 구분합니다. 기록은 다른 개인 파일과 함께 Git에서 제외되는 `local/`에 보관합니다.

## 정상 반영 확인

Codex 자동화의 최근 실행 결과와 `local/collection.json`의 마지막 성공 시각을 확인합니다. 화면의 기간은 기본적으로 **최근 2개월 전체**이며 달력에서 이번 주·이번 달 또는 직접 기간을 선택할 수 있습니다. 조회할 수 있는 데이터는 최근 2개월입니다. 최신 파일을 저장한 뒤 화면으로 돌아오거나 1분 기다립니다. 수집 실패 시에는 실패 원인을 해결한 후 같은 예약을 재실행하며, 경계나 완료 상태를 초기화하지 않습니다.

## 이고라이트 연결에 실패할 때

`Connection invalid`와 `Failed to start ego lite`가 함께 기록되면 수집 프로세스가 macOS의 브라우저 서비스에 연결하지 못한 상태입니다. 이 경우 로그인 만료라고 단정하거나 로그인 정보를 초기화하지 않습니다. Codex 채팅에서 수집 실행 권한과 브라우저 연결을 확인합니다. 화면에도 이고라이트 연결 실패 원인이 표시됩니다.

수집 CLI가 `workspace-write`로 실행되는 환경에서는 브라우저 앱 접근이 제한될 수 있습니다. Full Access로 바꾸려면 사용자가 허용 범위를 확인하고 직접 승인해야 합니다. 이 설정은 브라우저만 허용하는 옵션이 아니라 실행 프로세스의 파일 접근·명령 실행 제한도 해제합니다. 승인 없이 전체 Codex 설정을 바꾸지 않습니다. 권한을 유지하려면 브라우저에 접근 가능한 Codex 채팅에서 수집을 실행할 수 있습니다. [공식 권한 안내](https://learn.chatgpt.com/docs/agent-approvals-security)를 참고합니다.

## 수집 채널을 추가할 때

Discord와 Notion을 함께 확인하려면 기존 수동 수집 프롬프트와 정기 자동화의 수집 범위를 모두 갱신합니다. Notion 워크스페이스, 계정, 첫 수집 시작일과 로그인 브라우저를 지정하고 [Notion 수집 절차](COLLECT.md#notion-멘션을-함께-수집하기)를 따릅니다. `collection.json`에 서비스별 수집 지점을 보관하고, 신규 채널은 기존 Discord 경계를 재사용하지 않습니다. 두 서비스의 새 항목과 기존 미완료 후속 확인을 모두 끝낸 실행만 전체 성공으로 기록합니다. 실패한 채널의 경계는 유지하고 성공한 결과와 기존 수동 완료 상태는 보존합니다.

# 업무 데이터 형식

개인 데이터는 UTF-8 JSON으로 `local/tasks.json`에 저장합니다. 파일 전체는 배열이며, 항목이 없으면 `[]`를 사용합니다. JSON에는 주석이나 마지막 항목 뒤 쉼표를 넣지 않습니다.

## 업무 한 건의 예

```json
[
  {
    "id": "meeting-notes-20261022",
    "category": "requested",
    "kind": "question",
    "type": "planning",
    "project": "제품 개선",
    "initial": "todo",
    "date": "2026-10-22",
    "time": "11:15",
    "channel": "프로젝트",
    "sender": "나 → 동료",
    "title": "킥오프 회의록 정리 요청",
    "caption": "결과물 확인 대기",
    "author": "나",
    "quote": "회의록을 정리해서 링크를 공유해 주세요.",
    "note": "오후에 다시 확인을 요청했으며, 아직 완료 보고를 확인하지 못했습니다.",
    "url": "https://example.com/original-message",
    "evidence": [
      {
        "label": "후속 확인 요청",
        "url": "https://example.com/follow-up"
      }
    ]
  }
]
```

예시의 주소는 실제 원문 링크로 바꿉니다. 모든 링크는 `http://` 또는 `https://`여야 합니다. 접근 권한이 없는 원문은 앱에서도 열 수 없습니다.

## 필수 필드

| 필드 | 값·형식 | 사용 기준 |
| --- | --- | --- |
| `id` | 1~80자의 영문·숫자·`_`·`-`, 중복 불가 | 같은 작업은 재수집해도 유지합니다. 메시지 ID 등을 포함해 고유하게 만듭니다. |
| `category` | `mine`, `requested`, `question`, `shared` | 각각 내 할 일, 요청한 일, 내가 한 질문, 공유입니다. |
| `type` | `design`, `planning`, `review`, `marketing` | 각각 디자인, 기획, 리뷰, 마케팅입니다. |
| `kind` | `review`, `question`, `reference` | 리뷰 요청은 review, 공유는 reference, 그 외 요청·질문은 question입니다. |
| `project` | 프로젝트 이름 | 사용자 본인의 실제 프로젝트 이름을 입력합니다. 서로 다른 프로젝트는 분리하며, 선택 목록은 이 값을 그대로 사용합니다. |
| `initial` | `todo`, `done`, `reference` | 진행 중, 해결 완료, 공유 상태입니다. `shared`는 반드시 `reference`를 사용합니다. |
| `date` | `YYYY-MM-DD` | 원래 요청·질문·공유가 작성된 날짜입니다. 수집한 날짜와 구분합니다. |
| `time` | 24시간제 `HH:MM` | 메시지 작성 시각입니다. 사용자 시간대로 통일합니다. |
| `channel` | 채널·스레드 표시 이름 | 원문 위치를 찾을 수 있게 적습니다. |
| `sender` | 예: `동료 → 나` | 실제로 누가 누구에게 한 말인지 적습니다. |
| `title` | 짧고 구체적인 제목 | 무엇을 해야 하는지 드러나게 씁니다. |
| `caption` | 한 줄 설명 또는 빈 문자열 | 진행 상황·일정·검토 시 알아야 할 점을 간단히 적습니다. |
| `author` | 원문 작성자 | 봇 알림이면 봇임을 구분합니다. |
| `quote` | 원문에서 필요한 발췌 | 분류와 행동 판단에 필요한 부분만 포함합니다. |
| `note` | 맥락·현재 상황·판단 근거 | 완료 여부가 불확실하면 남은 확인 사항을 적습니다. |
| `url` | 원문 링크 | 작업 출처를 확인할 수 있어야 합니다. |

`category`는 관계, `type`은 업무 종류, `initial`은 해결 상태입니다. 예를 들어 내가 부탁한 디자인 리뷰는 `category=requested`, `type=review`, `kind=review`가 됩니다.

아이콘은 리뷰에 문서·돋보기를 우선 적용합니다. 그 외에는 요청한 일은 종이비행기, 내가 한 질문은 물음표, 공유는 공유, 내 할 일은 리스트를 사용합니다. 완료해도 업무 아이콘 구분을 유지합니다.

## 선택 필드

| 필드 | 형식 | 용도 |
| --- | --- | --- |
| `pr` | PR URL 문자열 | 별도 PR 열기 링크를 표시합니다. |
| `evidence` | `{ "label": "...", "url": "..." }` 객체의 배열 | 후속 답변·적용 확인·완료 근거를 연결합니다. |

## 프로젝트 구분

프로젝트는 설치한 사람이 직접 정합니다. 앱에는 특정 사용자의 프로젝트 목록이나 통합 규칙이 들어 있지 않습니다. 같은 프로젝트의 명확한 별칭만 통일하고, 관련이 있다는 이유로 다른 프로젝트를 합치지 않습니다.

예를 들어 `project`가 `아폴로`인 항목과 `종목필터 상품화`인 항목은 별도 선택 항목으로 표시됩니다. 개인적으로 합쳐 보고 싶을 때만 본인의 `local/tasks.json`에서 같은 이름으로 바꿉니다. 이 변경은 다른 사람의 설치본에 영향을 주지 않습니다.

## 수동 상태와의 관계

앱은 `local/state.json`에 같은 ID의 기록이 있으면 그 상태를 우선합니다. 수집 데이터를 갱신해도 직접 완료한 항목이 갑자기 다시 열리지 않게 하기 위한 규칙입니다. 새 요청을 기존 작업과 혼동해 같은 ID를 재사용하지 않습니다.

`local/state.json`을 수동 편집하는 대신 화면의 완료·되돌리기를 사용합니다. 업무 원문을 갱신할 때에는 `local/tasks.json`만 수정합니다.

## 저장 전 검사

```sh
python3 server.py --check
```

Windows에서는 `py -3 server.py --check`를 사용합니다. 형식 검사에 통과해도 실제 대화의 의미나 정책이 검증된 것은 아닙니다. 분류와 완료 판단은 원문·후속 결과를 별도로 확인해야 합니다.
